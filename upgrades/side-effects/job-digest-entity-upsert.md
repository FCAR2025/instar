# Side-effects review: job sessions upsert memory entities on a builder-written key

**Version / slug:** `job-digest-entity-upsert`
**Date:** `2026-11-07`
**Author:** `instar (evolution-proposal-implement job, EVO-002)`
**Second-pass reviewer:** `independent reviewer subagent (see below)`

**Summary.** Tier 1. `SessionActivitySentinel.materializeEntities()` now takes the session's `jobSlug`. For a job session it groups the extracted entities by type and upserts one entity per `(jobSlug, type)` on `source = "job-digest:<jobSlug>:<type>"`. The run that owns the entity is read from its `source_session`: another digest call of the same run merges its lines in (exact-line union); a new run replaces the content and first removes every `digest:` edge touching the entity, in either direction, so the edges on an entity always belong to the run that wrote its content. Every member is stored as one builder-written line, `- <name>: <content>`. Non-job sessions keep the exact-name path unchanged. `SemanticMemory` gains `updateContent(id, {content, lastVerified, sourceSession?})` and `removeEdgesTouching(entityId, contextPrefix)`, journaled as new `update` and `disconnect` actions that the JSONL replay applies. Files: `src/memory/SemanticMemory.ts`, `src/monitoring/SessionActivitySentinel.ts`, one new test file. Size: 2 source files, about 160 lines. Effort: three build passes. The review raised two concerns, fixed by moving the snapshot boundary to the run; its closed confirmation found one more instance of the same class (incoming edges), fixed by widening the edge rule to the whole edge surface; then a second closed confirmation. This is more rounds than a Tier-1 change usually takes, because the first design fixed instances rather than the edge-ownership class.

**Decision points.** One modified: the dedupe decision in `materializeEntities` pass 1. For job sessions it changes from "free-text name equals" to "builder-written source key equals". No block/allow surface.

1. **Over-block** — No block/allow surface. Within one job, all entities of one type merge into one entry, so two unrelated facts from the same job share one entry. Both are kept as lines of that entry, across every digest unit and call of the run that produced them (a run split into a Telegram unit and a session unit, or a periodic scan followed by the completion synthesis, keeps all of its lines).
2. **Under-block** — No block/allow surface. Each new run replaces the entry's content, so a fact that appeared only in an earlier run of the job is no longer in that entry. This is the intended "latest snapshot" behavior for recurring jobs. The same-run merge dedupes exact lines only, so one fact the model rewords between two units of the same run appears twice in that run's entry; this is bounded by the number of digest calls in one run and is cleared by the next run. Existing copies from before this change stay until memory-hygiene retires them.
3. **Level of abstraction** — The key is set where the entity is produced. `findBySource` already exists and is already used as an idempotency key by `MemoryMigrator`. Name comparison no longer promotes a match on this path.
4. **Signal vs authority** — No blocking authority added or changed. See `docs/signal-vs-authority.md`.
4b. **Judgment-point check** — No new static heuristic at a competing-signals decision point: "same job and same type" is an exact structural key, not a judgment.
5. **Interactions** — Pass 2 (relationships) is unchanged; links between entities of one group become self-loops and were already dropped. Because `connect()` dedupes on (from, to, relation) and keeps the first edge's context, a new run removes every `digest:` edge touching the keyed entity (outgoing and incoming) before pass 2, and pass 2 then adds this run's edges with this run's context. An interactive session's digest that linked to a keyed entity by its name loses that link at the entity's next run, by the same rule. Edges with any other context (for example a supersede reason) are never removed. Races: two sessions of the same job running at once would overwrite each other's lines and edges; the scheduler already skips a job that is still running (`JobScheduler.ts:1148`, per the second-pass reviewer). A job entity no longer merges into an existing non-job entity of the same exact name; it keeps its own keyed entry. Confidence is not changed by an update, so an entry that memory-hygiene lowered stays lowered. The FTS index follows the update through the existing `entities_fts_au` trigger; embeddings are refreshed fire-and-forget, as in `remember()`.
6. **External surfaces** — MEMORY.md shows at most one entry per job and type, named `<jobSlug>: latest <type>`. The JSONL journal gains `update` and `disconnect` lines; the journal's only reader is `SemanticMemory`'s replay, which now applies them.
6b. **Operator-surface quality** — No operator surface — not applicable.
7. **Multi-machine posture** — Machine-local by design: the store and its journal are per machine, as before. Each machine keeps its own keyed entry per job it runs. No notices, no URLs.
8. **Rollback** — Revert and ship a patch. Keyed entries stay as normal entities with their last content; a reverted build never updates them again (its job runs go back to adding name-keyed copies, which memory-hygiene retires). An older build replaying a journal ignores `update` and `disconnect` lines, so a rebuild on that build shows each keyed entry's first-run content and every edge any run added. No data cleanup is required for correctness.

## Conclusion

Clear to ship. The review changed the design: the snapshot boundary moved from each digest call to the run, read from the entity's own `source_session`, and edge cleanup became a journaled store operation.

**Round 1 — independent read of the artifact: concern.** Verbatim summary of the two findings, both shown with failing tests in `/tmp/claude-1002/evo-review/review-probe.test.ts`:

- Answers 1 and 2 were false for a run that spans more than one digest unit. Real wiring passes Telegram messages plus a tmux capture, so `ActivityPartitioner` can split one `digestActivity` call into two units, and `synthesizeSession` re-digests at completion after a periodic scan. Each unit called `updateContent`, so the last unit replaced earlier units of the same run. Input: job `health-check`, session `session-r1`, unit 1 fact "Disk usage 56%", unit 2 fact "Cert expiry". Outcome: the keyed content held only `Cert expiry: TLS cert expires in 3 days`. Suggested fix: merge when `existing.sourceSession === sessionId`; replace only when a new run writes.
- Answer 5 missed an interaction: edges from earlier runs stayed on the refreshed snapshot. Input: run 1's fact links to an existing tool entity "Docker"; run 2's fact has no link. Outcome: the run-1 edge (context `digest:session-r1`) still left the keyed fact. Suggested fix: on a new-run replace, drop the keyed entity's `digest:` edges, with a journaled `disconnect` action and its replay case.
- Note: answer 8's rollback text was inaccurate (a reverted build never updates a keyed entry again). Fixed in answer 8.

Resolution: root cause written first (class, mechanism, structural fix, proof); the snapshot boundary moved from each digest call to the run, read from the entity's own `source_session`, and edge removal became a journaled store operation.

**Round 2 — closed confirmation: concern.** Concern 1 closed; concern 2 closed only for outgoing edges. **Round 3 — closed confirmation: concur.** "The edge-ownership class is closed.
